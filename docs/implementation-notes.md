# Implementation notes

Developer notes that used to live in the README: how the pieces fit together, what moved where, and findings from building it. They overlap with the topic pages ([Music](music/index.md), [Home Assistant](home-assistant.md), [Settings page](settings-ui.md), [Architecture](architecture.md)), which are the better starting points; this page keeps the detail. Where a note says something has not run on real hardware, see the [status table](index.md) for what has been checked since.

## What moved out of QML into the core

Photo cycling, dashboard idle timeout, timer expiry/ring/snooze/auto-dismiss, music toggle state, the simulated voice sequence. QML now only renders and reports touches (`Store.activity()`). The HUD gains a **loop lag** line: how late a 50 ms asyncio sleep wakes up on the shared GUI/asyncio thread. That is the spec's "no GUI-thread call over 10 ms" gate (G2), measured directly.

## The live screen

While music is casting to the display or a timer is running, the resting screen is the live screen (`LiveScreen.qml`): a full-screen now-playing view, a full-screen timer, or up to three splits (music first, then the timers that finish soonest; extra timers get a "+N more" button). Tapping a tile opens its control view (`NowPlaying.qml`, `TimersSheet.qml`) over it; swipe up or Home goes to the dashboard. Core support: timers can be paused, resumed and extended from the display (`timer.pause`, `timer.resume`, `timer.extend`), except voice timers, which Home Assistant owns. Checked by scripted screenshots and real touch events on a Mac (`HAVENOS_SHOT=... HAVENOS_MUSIC_DEMO=1`), at 1280x800 and 800x1280; not on a Pi, so frame pacing is unmeasured.

## Settings web UI

Open `http://<device-ip>:8787` from a phone or laptop (port via `[web] port` or `HAVENOS_WEB_PORT`; `HAVENOS_WEB=0` disables it). It edits everything `config.toml` used to: Home Assistant URL + token, weather/media entities, quick-control tiles (with an entity picker filled from your HA), photo source (NASA Image of the Day, local folder or Immich with album picker and the recency sliders), and display timing, crossfade and blur. **Test connection** buttons check HA and Immich before you save; **Save & apply** takes effect live, no restart (`Core.apply_config`).

- **Sign-in:** a setup code shown only on the device (a QR code on first boot that opens the page already signed in; the gear on the dashboard shows it again) and stored in `~/.config/havenos/web_code`. Wrong codes are rate-limited (5 tries, then 60 s lockout). A good code gives an HttpOnly, SameSite=Strict session cookie (12 h); writes also need an `X-Requested-With` header. "Generate a new code" signs everyone out.
- **Secrets are write-only:** the API says whether a token/key is set, never what it is. They are stored in their own 0600 files (`ha_token`, `immich_key`), and `config.toml` only points at them; an inline secret from an older config is migrated out on the next save.
- Saving rewrites `config.toml` (comments are not kept; the previous file is saved as `config.toml.bak`). Settings overridden by `HAVENOS_*` environment variables are listed in the API (`env_overrides`) and still win.
- It is plain HTTP: use it on a trusted LAN, bind to 127.0.0.1, or put a TLS proxy in front.
- **Styling:** Tailwind CSS v4, prebuilt into `src/havenos/web/app.css` (committed, so no Node and no internet are needed to run). To change styles: `cd webui && npm install && npm run build`.

## Home Assistant device (ESPHome native API)

Opt-in (`[esphome] enabled = true`, the settings page, or `HAVENOS_ESPHOME=1`). havenOS then announces itself on mDNS and HA offers it under Settings > Devices & services > ESPHome. It exposes screen on/off, brightness, mode, photo next/previous, current photo, timers, a touch event (tap / swipes), diagnostics, and two services (`start_timer`, `dismiss_timer`). Design, the voice plan and a real-HA acceptance checklist are in `specs/04-esphome-integration.md`.

**Settings changed from HA persist.** Seconds per photo, crossfade, brightness and blur are written to `config.toml` (debounced by one second, flushed at shutdown, only when the value actually changed) by `core/persist.py`, so they survive a restart and show up in the settings page. Screen on/off, mode and the current photo deliberately do not persist: the display always boots awake on the ambient screen.

Verified with aioesphomeapi's own client in tests and from a separate process over mDNS, and adopted and used on a real Home Assistant. Plain text, no password unless you set `[esphome] key` (Noise encryption, required for voice): LAN only otherwise. The code is in `core/esphome/` and has a handler registry (`ESPHomeServer.add_handler`) that the voice satellite uses.

## Music (specs/07-music-pipeline.md)

`core/media/`: one **active source at a time, last to start playing wins** (`MediaCoordinator`), a small `SourceAdapter` contract, and a Sendspin source built on `aiosendspin`. The active source's track, art, position and transport show on the ambient strip, the dashboard music card and a full now-playing view (tap the strip); the Home Assistant media player is only shown when nothing is casting. State is `core.state["music"]`, commands are `music.command` (`toggle|play|pause|next|prev|seek|volume|mute|stop`).

- **Sendspin** is opt-in (`[music.sendspin] enabled = true` or `HAVENOS_SENDSPIN=1`): havenOS advertises over mDNS and Music Assistant adds it as a player. It declares the metadata and controller roles only, so it is a display and remote control for the group; it declares the **player** role (receives audio) only when an audio sink is supplied, and the audio worker/mixer does not exist yet.
- **Pairing:** Sendspin activates the metadata/controller roles only after the server pairs with us or trusts us. The pairing code is shown as an announcement on the display. Works with a real Music Assistant; the library screen below has only been tried against a fake one.
- **Spotify Connect** is opt-in (`[music.spotify] enabled = true` or `HAVENOS_SPOTIFY=1`) and needs `brew install go-librespot` and a Premium account. We run go-librespot as a child process (`manage = false` connects to one that is already running), read its API/WebSocket for state and control, and read its `pipe` audio from a FIFO. First time only: pick the device in the Spotify app (Connect's zeroconf login). **Known upstream problem:** on some accounts, Spotify refuses every audio key to librespot-based clients (`failed retrieving aes key with code 1`, go-librespot issues #279/#317, Premium or not, zeroconf or OAuth login), so nothing plays; the adapter detects a burst of these, stops, and shows a notice. It was seen on the author's Premium account, as it also was in Music Assistant's own Spotify provider. Plan on Spotify reaching the display through AirPlay or Music Assistant instead. Eviction stops playback and drops the session.
- **AirPlay** is opt-in (`[music.airplay] enabled = true` or `HAVENOS_AIRPLAY=1`) and runs `shairport-sync` as a child process, built with `--with-pipe --with-metadata --with-metadata-pipe` (and on the Pi `--with-airplay-2`; the adapter is the same for classic AirPlay and AirPlay 2). Audio comes from its pipe backend, state and cover art from its metadata pipe, and play/pause/next/previous go to the sender's own DACP service, which only some senders offer (Apple Music/iOS Music yes; Spotify and most third-party apps are display-only). On a Mac set `HAVENOS_AIRPLAY_PORT=7100`, because the system's AirPlay Receiver holds port 7000. Eviction pauses the sender if it can and restarts the receiver to drop the session. Verified end to end with a phone on macOS (classic AirPlay) and on a real Home Assistant setup. A paused sender stays on the display (a sender's "pause" is not the end of its session); a new sender interrupts the old one (`sessioncontrol` in the generated config).
- **Audio** goes through one shared mixer and one output (`core/audio/`): each source writes to its own stream on the mixer's media bus (resampled from Sendspin 48 kHz or AirPlay and Spotify 44.1 kHz to the output rate), gated so only the active source is heard, and the voice assistant plays on the announce bus. Ducking is the mixer's. It takes the system default output if that is stereo, else tries each stereo output; set `[music] audio_device` or `HAVENOS_AUDIO_DEVICE` (name substring) to choose, for example when the default is a Bluetooth headset.
- **Try it without any sender:** `HAVENOS_MUSIC_DEMO=1` adds fake AirPlay and Spotify sources; keys `1` AirPlay plays, `2` Spotify plays, `3` pause, `4` end, `m` now-playing view.
- **Library** (Music Assistant): set `[music.assistant] url` and a token (settings page, Music card, has a connection test). A Library button appears on the dashboard music card (key `L` on a desktop): browse recents, playlists and albums, search, tap to play on this display. Playing asks Music Assistant to start the display's own Sendspin player, so Sendspin must be enabled; the arbiter then treats it like any other source. Tested against a fake Music Assistant server only. Search by typing (a physical keyboard; there is no on-screen keyboard, by decision) or, with voice on, by speaking: the mic button in the search bar records one phrase, has Home Assistant's speech-to-text turn it into words, and searches for them. It does not go through Assist, so nothing you say is run as a command. Tested with fakes; not tried on real audio or a real speech-to-text provider.
- **Home Assistant:** with `[esphome] enabled`, the display is also a `media_player` (play, pause, stop, volume, mute), with title/artist/album/source sensors and next/previous buttons beside it. HA commands never take over the speaker.
- **Ducking:** music drops 20 dB (`duck_db`) while an announcement is up, a timer rings or the assistant is active, and returns over a second.
- **Also:** a toast on takeover, an opt-in "ready to cast" hint (`hint = true`), cover art cached by the core, a log warning when senders fight over the speaker, a Music card on the settings page. Pi units and `deploy/install.sh` are in `deploy/` (run on one Pi 4; no sound heard yet).
- **Not built:** the audio mixer in its own process (it runs in-process), multi-room sync, and the Pi gates. Crossfade on takeover was dropped from scope. (Home Assistant `play_media` URLs play as a music source; tested with a fake sound sink, not on real hardware.)

## Rooms, exposure, announcements

Everything from Home Assistant passes one rule: **only entities exposed to Assist are shown**, and it fails closed (see `specs/06-rooms-exposure-notifications.md`). The device finds its own room from HA's device registry (or the `room` setting); the quick tiles are that room's major exposed entities; a **Rooms** screen lists every room and lets you control its lights, climate, fans, covers, media, locks (unlock needs confirmation), scenes and vacuums; announcements take over the screen (`announce` service, with kinds and a countdown), and a bell opens the notification list. Touches go through an allowlist in `core/actions.py`.

## Integrations

- **Home Assistant** (`[homeassistant]` in the config): one WebSocket; weather (incl. daily/hourly forecasts via `weather.get_forecasts`), a media player, and up to 6 quick-control tiles whose tap action is chosen by entity domain. Without it the dashboard shows demo data. With it, nothing is faked: missing entities show "Unavailable", a failed call becomes an `error` event, a dropped connection reconnects with backoff, a bad token stops retrying and shows `auth_failed` in the HUD.
- **NASA Image of the Day** (`[photos] source = "nasa"`, the default): reads NASA's RSS feed (`https://www.nasa.gov/feeds/iotd-feed/`, no key, about 60 items), shuffles the images, and downloads each full-size original only when it comes up (some are 20 MB), then the usual downscale. A fresh shuffle each pass; same bounded cache and retry behaviour as Immich. Needs internet; with none the screen stays on its background and retries.
- **Immich** (`[photos] source = "immich"`): read-only. Lists image assets (an album, or random from the library) with a **recency preference**: the library is sampled in four age buckets (last 30 days, to 1 year, to 3 years, older) and each pass of `list_size` photos is a weighted draw whose weights halve every `recency_half_life_days` (default 365) down to a floor of `recency_floor` (0.1), so recent photos come up more but old ones still do. Against the real library that gave roughly 44% last 30 days, 34% last year, 16% 1-3 years, 6% older. Downloads the ~1440 px **preview** rendition rather than the original, then the usual downscale. The playlist keeps `history` photos for swipe-back and `prefetch` ahead, and deletes cache files as they age out, so disk and RAM stay bounded. Broken assets are skipped; if the server is down the screen keeps retrying every 10 s.
- The HUD shows photo source, cached-photo count and HA status.

## Findings so far

1. **Use `qasync`, not `PySide6.QtAsyncio`.** QtAsyncio's loop has no network I/O: an aiohttp server or client hangs on first use (6.12, macOS). qasync runs aiohttp, WebSockets and `ProcessPoolExecutor` directly. (An earlier note here said QtAsyncio was fine; that was only true for sleeps, tasks and thread pools.)
2. `engine.rootObjects()[0]` is a plain `QWindow` wrapper; wrap with `shiboken6.wrapInstance` to get `QQuickWindow` (`grabWindow`, `rendererInterface`).
3. `None` crosses to QML as `undefined`, not `null`; the facade normalises it.
4. Core state uses plain dicts/dataclasses, not pydantic.
5. **Headless screenshots lie about blur.** Under `QT_QUICK_BACKEND=software` the portrait backdrop blur and glass blur do not render (black sides, flat panels). That is a test-environment limit, not a regression. Judge glass in the real window.
6. If a process-pool worker dies, `run_blocking` falls back to threads instead of failing every later photo.
